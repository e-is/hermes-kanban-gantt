# Porting a standalone web app into a plugin: the user's standing conventions

Moved out of SKILL.md (it applies to the port, not to every plugin task).

When porting an existing standalone web app (FastAPI + React) into a plugin, apply these standing user rules from the start:
- NO authentication layer: the plugin runs inside the authenticated Hermes desktop context, so drop login/session checks, `/api/auth/*` routes, and any anonymous/localStorage fallback — data (profiles, settings) is always persisted backend-side via `plugin_api.py`.
- NO dark/light theme toggle: the desktop shell owns theming through its CSS vars (`--ui-*`); a hardcoded theme switcher fights the shell.
- Backend port is a mechanical adaptation (FastAPI `app` → `APIRouter`, data dir re-pointed into the package); keep the reference app's routes and shapes so its existing tests port with minimal edits.
- The consumption/usage half of a dashboard app is a SEPARATE plugin (different release cycle) — split repos rather than shipping one mega-plugin.
- Score/profile selectors bind to the desktop's own identity, not the reference app's seed data: list the user's Hermes profiles from a backend endpoint that reuses `hermes_cli.profiles` (`list_profiles()`, `'default'` first, `['default']` fallback) and render them as pill chips in the settings-scope style (`rounded-full` border, active = `--ui-stroke-secondary`/`--ui-bg-tertiary`; copy `apps/desktop/src/app/settings/profile-scope.tsx`). A selected profile with no saved weights is synthesized at selection time with the agreed defaults (everything 0 except intelligence 5 and price 3) and named after the profile id — NEVER fall back to a hardcoded seed profile name (a 'default' chip silently scoring with a seed role's weights and label is the bug the user spots first).
- Every new backend endpoint gets a pytest case BEFORE deploy; mock external processes (`monkeypatch.setattr(subprocess, 'run', ...)` for one-shot LLM calls via the `hermes` CLI) so tests never hit a real model. Import helpers the endpoint uses at MODULE level (`import shutil`) if tests monkeypatch them as module attributes.
- Commit in SEPARATE commits per half (backend+tests / frontend+build+artifact / docs) so a bad half can be rolled back alone; push only after the user's on-screen validation.
- **Sidebar nav label is NOT the plugin id**: the `register({ route: { label } })` in `main.tsx` determines what appears in the desktop's sidebar. A generator default (the plugin repo directory name, e.g. `plugin-llm-leaderboard`) shows the raw label the user's site testers cannot find. Set `label: 'Model Leaderboard'` (user-facing name) explicitly; the path/route key is separate.
- **First run seeds from the user's own config, not from shipped seed data**: when the plugin keeps an editable list (tracked models, watched feeds…), an empty/absent store must be seeded from what the Hermes installation already declares — for models, the main model of every installed profile, read via `hermes_cli.profiles.list_profiles()` → `<profile path>/config.yaml` → `model.default` (`'default'` profile first; accept `default`/`name`/`model`/`id` keys when `model` is a dict, or a plain string). Persist the seed so the next boot reads it instead of reseeding. Guard the seed to return `[]` when `hermes_cli` is not importable, so unit tests never touch the network, and degrade a failed upstream lookup to an entry flagged `available: False` rather than raising — a shipped seed JSON stays as last-resort fallback, never the primary source.
- **Search/external-results checkbox pattern**: a checkbox gate next to the search input controls whether the search also hits the external /api/search endpoint. The checkbox state gating applies to BOTH the search() function call (`if (!searchUntracked) { setSearchRes([]); return }`) and the results block render (`{searchUntracked && searchRes.length > 0 && ...}`). The untracked results display between the toolbar and the tracked-table heading.
- **README shape the user asks for**: an `## Install` section immediately after the intro paragraphs — the exact `hermes plugins install <owner/repo> --force` / `hermes plugins enable <manifest-name>` / `hermes gateway restart` trio, then the three traps spelled out (the CAUTION scan verdict that makes `--force` the intended path, the plugin key being the manifest `name:` and NOT the repo name, and answering NO to the tool-override prompt because the plugin registers no agent tools). And a roadmap split **Done / Next / Later** rather than one flat TODO list: check shipped items off instead of deleting them, so the next reader sees what recently changed.
- **Measure a data source before building a sync on it.** For each candidate source, resolve its entries against the ACTUAL tracked items and count real matches, then eyeball a few: a fuzzy matcher over a stale leaderboard yields plausible WRONG numbers (a 4.6-generation model pinned to its 4.0 row) which are worse than an empty column. Prefer dropping a stale curated column over syncing it; keep what stays curated with its source and date surfaced in the UI, and document the auto-vs-curated split in the README. The measured status of every benchmark/language source tried so far, with re-probe one-liners, is in `references/data-sources-benchmarks-and-languages.md`.
- **Rating criteria must be independent.** The user rejects a criterion that restates two criteria already rated separately: a `tools_vision` flag multiplying the tools and vision scores double-counts the same two capabilities and is removed on sight. Before adding a criterion, check it measures something not already covered; a combined bonus only earns its place when the combination is genuinely multiplicative in the real work, and even then it is offered as its own clearly-named criterion rather than a silent multiplier.
- **Removing a criterion (or any feature dimension) is a full sweep, not a deletion.** The places that carry a criterion, all of which must be found: the criteria list, the radar/spider axis list, the default weights object AND the seeded profiles JSON, the scoring core (the component plus its entry in the returned breakdown), BOTH locale bundles (label + description keys), the backend's criteria doc / seeded profiles / score output, the shipped data files, the tests (weight fixtures and any dedicated case for the removed helper), and the README's stated criteria count. Completion criterion is a repo-wide `grep` for the key name and its camelCase variant returning nothing — a green build proves none of it, since an orphaned criterion key is still valid code.
